# 0003. Auth bootstrap: CLI-issued sign-in link, then passkeys

Date: 2026-10-04

## Context

Better Auth's passkey plugin requires an authenticated session to register
a passkey, and the brief rules out a sign-up flow: the single account is
seeded by a CLI script. Something has to produce the _first_ session.

Options considered:

1. Email + password on the seeded account. Simple, but adds a password
   to an app that is supposed to be passkey-only.
2. `registration.requireSession: false` with a `resolveUser` callback.
   Lets anyone who can reach the server register a passkey for the owner.
3. A magic link generated by a CLI command and printed to the terminal.
   No email is sent; the link is consumed in the browser.

## Decision

Option 3.

- `bun run db:seed` inserts the single user row (email from
  `BLOOM_OWNER_EMAIL`). Runtime user creation is blocked: the magic link
  plugin runs with `disableSignUp: true` and a `databaseHooks.user.create`
  guard refuses any other insert.
- `bun run auth:link` asks Better Auth for a magic link for that user and
  prints it (15-minute expiry). Opening it creates a session and lands on
  `/passkeys`, where "Add a passkey" registers the device.
- From then on `/login` offers "Sign in with passkey" (with WebAuthn
  conditional UI). The CLI link remains the recovery path if every passkey
  is lost.

## Consequences

- No password exists anywhere.
- The bootstrap requires shell access to the server host, which is the
  intended trust boundary (Tailscale-only).
- iOS device tokens later: issue through a Better Auth bearer/device flow
  behind the same session model.
